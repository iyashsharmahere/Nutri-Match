# NutriMatch

Daily meal plans calculated from your body, goal, diet and allergies, using only foods from a measured dataset of ~1,600 Indian dishes.

## How it works
1. **Target**: Mifflin-St Jeor BMR × activity multiplier, ±calories for your goal (floor 1,200 kcal).
2. **Filter**: diet type, allergens and any foods you've hidden are removed first (UI labels are mapped to the dataset's labels, e.g. Dairy → Milk/Dairy). Condiments, sides, plain flatbreads and rows whose macros contradict their energy are excluded.
3. **Match**: nutrients are standardised with a scikit-learn `StandardScaler` fitted on the dataset; foods are ranked by cosine similarity to each meal's share of your target (Breakfast 25%, Lunch 35%, Snacks 15%, Dinner 25%).
4. **Portion**: each meal gets the portion size (0.5×–2×) closest to its calorie share.

Nothing is generated by an LLM; every food and number comes from `backend/data/foods_modified_reviewed.xlsx`.

## Features
- **Day plan** with portion sizes, swap, shuffle, and “never suggest this again”
- **Week planner**: 7 varied days, no dish repeats within 2 days, every day within ~15% of your calorie target
- **Grocery list** built from each dish's recipe, scaled by portion, grouped by aisle, tick-off state saved, copy or print
- **Nutrition check**: macro split, calories per meal, fibre / calcium / iron / vitamin C / sodium / sugar
- **Food library** with search, filters and full nutrition per dish
- **3D elements** (Three.js): a plate whose sections are your macro split with produce drifting around it, a tomato plant in the page margin that grows as you scroll and ripens at the bottom, a tiltable calorie dial on the plan page, and a week skyline of bars you can click to pick a day
- Plan is saved in your browser, so a refresh never loses it

## Run it
**Windows:** double-click `run_nutrimatch.bat`.

**Manually**
```bash
# terminal 1
cd backend && pip install -r requirements.txt && python -m uvicorn main:app --reload --port 8000
# terminal 2
cd frontend && npm install && npm run dev      # http://localhost:5173
```
To point the app at a deployed API, create `frontend/.env` with `VITE_API_URL=https://your-api`.

**Tests**
```bash
cd backend && pip install -r requirements-dev.txt -c constraints.txt && python -m pytest -q
cd frontend && npm run lint && npm test      # `npm test` needs the API running: RATE_LIMIT_PER_MIN=0 uvicorn main:app
```
**Real-browser checks:** `cd frontend && npm run build && npx vite preview --port 4173` (with the API running), then `CHROME_PATH=/path/to/chrome npm run e2e`. These cover what the jsdom tests can't (CSS layout): the plant is fixed in the margin, grows as you scroll, never overlaps text at six screen sizes, and clicking a skyline bar selects the matching day.

CI (`.github/workflows/ci.yml`) runs all of it. **Docker:** `docker compose up`.

**Refresh the food library** after editing the spreadsheet: `cd backend && python scripts/export_foods.py`

## Configuration (environment variables, backend)
| Variable | Default | Purpose |
|---|---|---|
| `ALLOWED_ORIGINS` | `*` | Comma-separated sites allowed to call the API. **Set this in production.** |
| `RATE_LIMIT_PER_MIN` | `60` | Per-client limit on planning endpoints; `0` turns it off |
| `TRUST_PROXY` | `0` | Set `1` behind a reverse proxy so the real client IP is used for limiting |
| `LOG_LEVEL` | `INFO` | Logging verbosity |

Frontend: `VITE_API_URL` in `frontend/.env` (see `.env.example`).

## API
Interactive docs at `/docs`. Probe: `GET /health`.

| Endpoint | Purpose |
|---|---|
| `POST /api/recommend` | One-day plan. Add `seed` for a different valid plan, `avoid_foods` to hide dishes |
| `POST /api/recommend/week` | Seven varied days |
| `POST /api/recommend/swap` | Alternatives for one meal slot |
| `GET /api/foods` | Paged, filterable food list |

Inputs are validated strictly: unknown goals/diets/activity levels, out-of-range numbers and oversized lists return `422` with a readable message instead of silently using defaults. Every response carries an `X-Request-ID`; 500 errors show only that reference, with details in the server log.

## Design decisions
- **Scaler is fitted at startup**, not unpickled: no pickle-loading risk, no scikit-learn version drift, and it matches the dataset actually served.
- **Filters are precomputed once** and matching runs on a standardised numpy matrix, so a day plan takes ~20 ms and a week ~100 ms.
- **Protein is capped at 35% of calories** so heavier users on low targets never get macros that add up to more than their energy.
- **The UI keeps a snapshot of the inputs a plan was built from**, so editing the form without submitting can't mislabel the plan on screen.
- **Saved browser state is validated and versioned**; corrupt or outdated saves are ignored rather than crashing the app.
- The rate limiter is in-memory, which suits one process. Run several instances and enforce limits at the proxy (or move counters to Redis).

## The 3D layer (`frontend/src/gl`)
- **Loaded on demand.** Three.js (~128 KB gzipped) is its own chunk, fetched only when a 3D element mounts; the main bundle stays ~68 KB.
- **Always has a flat fallback.** No WebGL, a very low-memory device, or a failed load shows the plain version (a text card, a CSS ring, CSS bars). Every number shown in 3D also exists as real text.
- **Respects reduced motion.** With `prefers-reduced-motion`, nothing animates by itself; frames draw only when you scroll, drag, or the data changes.
- **Cheap when idle.** Rendering pauses when a scene is off-screen or the tab is hidden, and GPU resources are released on unmount.
- `helpers.js` holds the pure maths (shares, colours, layout) with no Three.js import, so React code can use it without pulling Three.js into the main bundle.
- Three.js is pinned to **r162**, the last release that still supports WebGL 1, which lets the scenes be rendered headlessly for visual checks. To upgrade, change the version in `package.json`; the scene code doesn't depend on r162 features.
